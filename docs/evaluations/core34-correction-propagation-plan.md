# Core #34: prospective prose-linked correction evaluation

Baseline: development main `99f0bec3f7aa24e446a2470432709a242c483f26`.
Status: bounded existing-contract evaluation, not a new correction schema.

## Owed outcome

Evaluate whether a genuinely fresh consumer can repair a stale capability
interpretation from durable Evidence, using the existing reference host and
current protocols. Do not seed a corrected Knowledge answer into the fixture.

The producer saves one correct performance and provisional Knowledge. A second
session appends a later neutral learner self-report: its ordinary observation
prose names the original Evidence ID and reports that a hint supplied the
explanation, while the learner recalled the labels independently. That session
ends before Knowledge reconciliation. Original performance bytes remain intact.

Fresh read-only recovery uses no producer Evidence ID: discovery identifies
Evidence and its Knowledge owner; a final bounded combined read checks all
selected version tokens against one snapshot. A model receives only that result
and current product protocols, and proposes any justified reconciliation. The
exact first request is replayed through the existing owning operation. The
fixture does not substitute a repaired request when the first one fails.

## Prospective acceptance

The frozen `tests/fixtures/core34-correction/prospective-manifest.json` owns the
first-output criteria and packet hashes. Three fresh contexts receive structured
state, a same-fact strong summary, or structured state without the correction
report. They see no oracle or prior model output. A further fresh consumer receives
only the durable result after an admitted correction request.

Acceptance is semantic, not exact text: narrow the unsupported independence
assumption without inventing inability, a failed performance or mastery; retain
one source occurrence; preserve the unaffected label-recall claim; keep neutral
Evidence out of support/challenge lists; select a proportionate teaching action.
Keeping an appropriately qualified original support reference or removing it is
acceptable when justified. A diagnostic is optional. No arm must choose an
artificially different action to demonstrate sensitivity.

Deterministic checks cover create-only preservation/retry, fresh discovery,
read-only recovery, exact-request replay, bounded references, neutral-direction
rejection and stale-token rejection. Semantic output review is separate from
these storage/gate checks. All first outputs, including failures, remain frozen.

## Existing owners and unresolved semantics

Schema section 21 and persistence sections 3/5 permit an appended reinterpretation
event. Classification requires separate self-report and reassessment of confounds.
Integration prefers refinement and delegates the semantic judgment to the
consumer. Knowledge's existing `basis_summary` can retain a concise qualifier.

There is no settled typed correction relation, per-target supersession rule or
neutral-context reference list. `source.round_id` describes assistant-turn
provenance and is not an occurrence identity. Discovery emits one row per record;
reconciliation checks direction/target for newly added refs, not independence.
This experiment therefore cannot prove automatic same-occurrence grouping,
validated relationship traversal, supersession, or general correction safety.

If typed correction is needed for the wider #34 outcome, the recommended next
decision is an explicit target-scoped reinterpretation link to an existing
Evidence record, with later-report time separate from original performance time,
and a traceable neutral interpretive-context reference. Its meaning should be
“reassess this claim using this context,” never automatic latest-wins, a second
independent performance, or automatic state downgrade. The trade-off is stronger
recoverability/validation versus a schema and host-admission change; prose avoids
that change but leaves interpretation and relationship validation to the model.
Link shape, repeated/conflicting corrections and handling of dangling or
out-of-scope links require product settlement before implementation.

## Limits and publication

Native consumers are same-model-family evidence, not independent audit. They are
explicitly asked to consider durable updates, so this is prospective prompted
semantic repair rather than unprompted ordinary adoption. Shared-workspace
isolation is instructional; hard filesystem blinding is not established.

The 28 historical scenarios stay `not_executed`, and earlier #39 failures stay
failed/inconclusive. No production code, transport, service, schema, live learner,
Instance, deployment pin, provider or spend change is included. No closure of
#34 or teaching-effect acceptance follows. Remote feature-branch/PR publication
requires the current task's explicit approval and exact-head pre-review gate.
